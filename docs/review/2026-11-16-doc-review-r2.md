## 3. 新增阻断（D6）

### D6　凭证写回顺序仍不可实现：接口与流程相互矛盾

- **位置**：`docs/design.md` §3.2（接口注释）、§3.3 步骤 2/3、§3.4 第 1 条。
- **矛盾点**：
  1. §3.2 接口注释仍是「`UpdateCredential` 校验并应用新凭证」；§3.4-1 仍是「应用新值到 Client → 网络验证 → **成功则 `discoverCloudHost` + `saveTokenState`**」。即：**内存凭证与 token state 都在 `UpdateCredential` 内部完成，且发生在 main 写 config 之前**。
  2. 而 §3.3 规定顺序为 a. 写 config → b. 加锁切换内存凭证 → c. 写 token state。步骤 2 已经切过内存、已经写过 token state，步骤 3b/3c 变成重复动作或空操作。
  3. 步骤 3 的失败回滚写「驱动凭证换回旧值」，但 `CredentialUpdater` 只有 `UpdateCredential`——**没有回滚方法**。重调 `UpdateCredential(旧值)` 会再走一次 10 秒网络验证，且此时 config 已是新值，状态更乱。
- **为什么是阻断**：这是 v0.10.0 的核心写路径，按现文档实现，要么顺序落不了地，要么出现「config 写失败但内存已生效」的不可回滚状态——正是 RV-01 D5 要解决的问题。
- **要求**（三选一，写进 §3.2/§3.3，并让 §3.4 与之逐字一致）：
  - **(a) 两阶段接口**：`Validate(ctx, values) error` + `Commit(values)` + `Abort()`；main 在 Validate 成功后写 config，成功后 Commit，再写 token state。
  - **(b) 返回回滚闭包**：`UpdateCredential(...) (rollback func(), err error)`——驱动内部暂存旧值并只做「生效 + 验证」，由 main 在 config 写失败时调用 `rollback()`（同步、不联网）。
  - **(c) 明确接受顺序倒置**：写死「驱动先生效并落 token state → main 写 config → 写失败则用 `.bak` 恢复并重启进程」。此方案最简单，但必须写明「失败即重启」的语义与验收项，并确认移动驱动重启后以 `config.json` 为准、token state 不会把旧值顶掉（`drivers/mobile` 无 token 新旧比较逻辑）。
  - 无论选哪种，`saveTokenState` 的调用点必须唯一：只在 main 侧成功路径调用（(a)/(c)），或只在驱动 Commit 中调用（(b)），不得两处都写。

## 4. 新增重要（I8–I14）

### I8　报告改名后，约 25 处代码相对链接全部失效（P6 回归）

- **清单（按节）**：§4.4（1 处）、§5.2（6 处）、§8.2 表格（8 处）、§12.C（10 处）。
- **影响**：D1/D3 的证据链、§8.2 的修改清单都靠这些链接定位；审阅者与后续开发者会直接撞 404。
- **要求**：统一改为仓库根绝对路径（`/internal/webdav/prop.go`，GitHub 支持）或 `../internal/...`；改完后抽查 3 条可点击。
- **附带**：`README.md` 本轮未改（仍是 aeb928e 内容），其"项目结构"未含 `docs/` 与 `docs/review/`——按闸门⑥ 属发布前动作可接受，但建议在 `design.md` §5 或 `CLAUDE.md` 记一句「README 随 v0.10.0 发布更新」，避免被当成遗漏。

### I9　`vault.paths` 的书写格式两份文档冲突

- **冲突**：`design.md` §4.3 与 `TODO.md` 拍板——「`vault.paths`（根目录名列表，如 `["backup", "Archive"]`）」；报告 §7.8 配置示例与 §1.1 需求 5、§0 摘要、§7.2 请求流程——`["/backup", "/Archive"]`、`/天翼个人/backup/...`。
- **影响**：配置解析到底按"首段名字"还是"绝对路径"实现，会直接决定匹配逻辑与 `_mc` 屏蔽范围；两份文档各写一套，实现者必然挑一个，另一个成为口径错误。
- **要求**：定死一种并在三处同步（design §4.3、报告 §1.1/§7.8、TODO 已拍的条目下补一句"格式：无前导斜杠的目录名"）；同时写明匹配规则——`Handler` 已 strip 掉 `/<mount>` 前缀，因此 Vault 收到的是挂载内相对路径，只需比较首段字符串（大小写敏感，与原盘一致）。

### I10　"上游返回 200（忽略 Range）→ 流式丢弃到起始偏移"在 55 GB 场景不可行

- **位置**：报告 §7.4「上游异常分支」表第 1 行。
- **分析**：该策略等价于从 0 开始解密并丢弃到请求偏移。对实测的 55 GB 文件、`bytes=50000000000-...` 的拖动请求，意味着先下载 50 GB 才能开始返回——4K 拖动必然超时，Phase 1 验收「拖动 10 次不失败」不可能过。
- **要求**：改为分级策略并写进表：
  1. 200 视为上游拒绝 Range → 关闭流，**用新签名 URL 重发一次**（换节点/换签名常能恢复 206）；
  2. 仍是 200：若偏移 ≤ N 块（建议 N=2，即 ≤2 MiB）→ 允许丢弃；否则返回 **502**（并在日志中记录"上游不支持 Range"，便于 PM 判断该盘是否可用）；
  3. 明确不做"整文件顺序转发"降级（会占满路由器带宽且破坏 seek 语义）。
- **附带**：表里「206 的 Content-Range 与请求区间不符 → 关闭重试一次」需补一句"重试前是否失效 URL"（与 §5.4 的 403 刷新共用同一把刷新锁）。

### I11　Vault 绕过 RetryReader 后失去重试；`List 走 cached` 的注释自相矛盾

- **事实 A**：按 D1 的处置，Vault 对 vault 路径直接调 `raw.Link`，链路变成 `Vault → raw`，**跳过 `RetryReader`（3 次 / 500ms）**。云盘 API 抖动时 Vault 路径比 302 路径更脆。
- **事实 B**：`design.md` §4.1 与报告 §8.2 的示例注释写「List 走 cached（虚拟树在内存，不命中上游）」——两句自相矛盾：虚拟树既然在内存，就不该经过 cached；若真经 cached，则虚拟树结果会被缓存 30 秒，manifest 更新后目录延迟与内存占用都会失控。
- **要求**：
  - 注释改为两条独立规则：「`/M/<vault>` 前缀 → List 读内存虚拟树、Link 走 `raw`（自管 URL 表）；其余路径 → List/Link 全部委托 `cached`」。
  - 明确 Vault 对 `raw.Link` 的失败是否自实现重试（建议：仅对网络错误重试 1 次，与 `RetryReader` 的 "not found 不重试"语义对齐），或写明"接受无重试"及理由。

### I12　fileID 一致性校验成本极低，建议提前到 Phase 0

- **位置**：报告 §7.3 不变量 4、§9 Phase 0/Phase 1。
- **分析**：PM 拍板的是"防偷换/回滚的**强校验**放 Phase 1"，指的是 `metadata.p` 路径比对、失败策略等。而「manifest 记录的 fileID == 对象头 fileID」只需读 64 B 头部即可比对（本来就要读），成本≈0，且能挡住最常见的"把 b 的对象挂到 a 的名字下"。
- **要求**：文档把两条校验拆开表述：fileID 一致性 → **Phase 0 必做**（写进 §9 Phase 0 验收）；`metadata.p` 路径比对与失败处置 → Phase 1。这样既不违反 PM 拍板，也不把零成本防护推迟。

### I13　§11「三家均 206」与 §4.5「百度待测」矛盾（RV-01 口头提出、归档件漏记）

- **事实**：报告 §11 最终结论表写「CDN Range 是否支持 | **支持**，三家均 206」；§4.5 汇总表明确"百度网盘：待测"，§4.4 也写"本轮没有重新执行百度的 302/Range 测试"。§0 摘要写的是"天翼个人/家庭、移动均返回 206"，与 §4.5 一致。
- **说明**：该条在 RV-01 口头意见中提过，但整理归档时漏进报告，属**评审自身遗漏**，此处补记。
- **要求**：§11 改为"三家测试对象（天翼个人/家庭、移动）均 206；百度走代理路径，Range 待实测"，与 §4.5 对齐。

### I14　文件头的 `key_id` / `flags` / `reserved` 未定义语义

- **位置**：报告 §7.3 文件头表 + §7.5 密钥层级。
- **问题**：头部有 8 B `key_id`，但 §7.5 只有一个 master key + HKDF，全文未说 `key_id` 写什么；`flags`、6 B `reserved` 也无"Phase 0 写全零"的约定。格式一旦被 `cmd/mcrypt` 写错，Phase 2 的密钥轮换就没有兼容基点。
- **要求**：§7.3 补一段字段语义：`key_id = SHA-256(masterKey)[0:8]`（或明确"恒为 0，Phase 2 启用"）；`flags` 与 `reserved` 在 Phase 0 必须写零，读取时"非零即拒绝"或"忽略但保留"（二选一写死）。
