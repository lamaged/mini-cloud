**新增两处值得肯定**：

1. **物理三层 / 虚拟层级精确化**（`容器/明文目录/_mc`，单元间不嵌套；单元内部允许多级虚拟目录）——把"扫描识别到第几层"这个此前最大的歧义一次性钉死，是良好的设计收敛。
2. **子目录原子单元模型**（整体加/整体删，拒绝就地修改与层级变更）——把"更新"重定义为"删旧传新"，规避了部分更新带来的中间态与一致性负担，符合低复杂度原则。

## 2. 实现期建议（不阻断，4 条 P 级）

| 编号 | 内容 | 建议 |
|---|---|---|
| P7 | 嵌套 `_mc`（违反固定三层）会被静默视为普通目录 | 扫描只识别第二层 `_mc`；若用户误把 `_mc` 放到第三层（`dir/子/_mc`），该子树被当普通目录——密文对象可被 302 枚举/下载，且用户误以为已加密（无明文泄露，但属"加密未生效 + 元数据暴露"）。建议实现期：扫描时对子目录再做一层 `List`，发现更深层 `_mc` 即告警（或文档明确"仅识别第二层，更深层视为普通数据、用户自负"） |
| P8 | 整块换新/就地覆盖会残留旧对象 | 原子替换语义下每次换新都会留下无主 `_mc/o/*.bin`（新 manifest 不引用）。建议文档提示"换新后清理旧 `_mc/o` 残留"，或 Phase 2 顺带在 mcrypt 提供 `--clean`；否则长期累积占云盘且泄露"该目录曾更新过"的痕迹 |
| P9 | 异步扫描 goroutine 的 ctx 语义未写 | 扫描已与触发请求解耦，应使用**后台 ctx**（非请求 ctx），仅受每目录 ≤5s 超时约束；实现期在 `refreshMu` 与 goroutine 创建处注明，避免误传请求 ctx 导致扫描在客户端断开后被取消 |
| P10 | 「就地覆盖」与「拒绝就地修改」措辞需区分 | 正文使用模型写"拒绝就地修改"，而验收 #2 含"就地覆盖变体"。二者实为"整块替换（覆盖整个 `_mc`）=允许；单个文件就地改=拒绝"。建议正文补一句明确，避免实现/验收歧义 |
