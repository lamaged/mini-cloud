## 1. 复核结论

1. **两项实现级缺陷均已实质修复，且未引入格式变更**——`Metadata.H` 以"废弃字段 + 注释"方式处理，`CipherSize` 为纯方法修正，**存量对象无需迁移、无兼容性风险**，这是本轮处置最正确的取舍。
2. **I3 的处置方式恰当**：Phase 0 不具备云端上游，无法在代码层验证顺序流式；以 PM 拍板方案 (b) 将契约写入 `design §4.1` 与报告 §7.4，把实现责任明确落到 Phase 1 的 `upstream.go`，避免"文档承诺与实现不符"的悬空。
3. **新增观察全部集中在文档一致性与边缘健壮性**，不影响 Phase 0 核心正确性。
4. **Phase 0 完成度需澄清**：本轮完成的是"库层"（格式/加密/读取器/mcrypt），Phase 0 验收清单中依赖 Vault 包装层的三项（`_mc` 403、WebDAV 206、local 驱动接入）尚未具备执行条件——建议在 PROGRESS 中区分"库完成"与"Phase 0 验收通过"。

## 2. 逐条复核

| 编号 | 意见 | 结论 | 代码级证据 |
|---|---|---|---|
| I1 | 元数据先于哈希计算加密，对象内嵌 H 恒空 | **关闭** | `EncryptObject` 签名改为 `(*Header, string, error)`，返回权威 SHA-256（hex）；`cmdEncrypt` 以返回值写入 `Entry.SHA256`；删除对已序列化结构体的无效回写；`Metadata.H` 保留字段并注明废弃（读取方不得依赖）。**唯一真值源 = manifest.Entry.SHA256** |
| I2 | CipherSize 对非对齐明文多算 | **关闭** | `CipherSize = DataOffset + uint64(PlainSize) + ChunkCount*TagSize`；`format_test` 更新既有断言并新增 1.5 MiB 非对齐用例；空文件退化为 `= DataOffset`，与原契约一致 |
| I3 | 顺序读 = 每块一次 ReadAt | **关闭（拍板方案 b）** | `design §4.1` 增「顺序流式 RangeSource（长连接 + 内部缓冲，顺序播放不按块发请求；随机 Seek 走单块）」；报告 §7.4 同步改写原承诺；TODO 记录 PM 拍板。Phase 0 本地按块 ReadAt 已注明无网络开销 |
| P1 | 读 meta 未检查 ReadAt 的 n | **关闭** | `n, err := src.ReadAt(blob, HeaderSize)`；`err != nil && err != io.EOF` 单独处理；`n != int(h.MetaLen)` → 「元数据被截断」。新增 `shortMetaSource` 用例（短读且 err==nil 场景） |
| P2 | keygen 未收紧存量 vault.key 权限 | **关闭** | `WriteFile` 后显式 `os.Chmod(path, 0600)`，失败即返回错误 |
| P3 | encrypt 未拒绝 out 位于 in 内部 | **关闭** | `filepath.Abs` 后做「相等或前缀 + 分隔符」判定，命中即 `errors.New` 拒绝 |
| P4 | 符号链接静默跳过 | **关闭** | 跳过分支打印「跳过 `<虚拟路径>`（非普通文件）」 |
| P5 | Read 无 c==0 防御 | **关闭** | `copy` 结果为 0 时返回 `io.ErrUnexpectedEOF`；空文件在循环前已由 `offset >= PlainSize` 返回 EOF，不产生误判 |
| P6 | meta AAD 零占位原因补文档 | **关闭** | 报告 §7.3 增 v1.3 修订块，含「h 废弃」与「meta AAD 为何不绑 MetaLen/DataOffset；分块 AAD 绑完整头；空文件由 header_sha256 兜底；勿改成绑定完整头」的因果说明 |

**格式兼容性核对**：`Metadata.H` 保留为字段（仅废弃语义）、`CipherSize` 为方法、`Metadata.S` 仍由调用方在 `SealMeta` 前设置——**磁盘格式零变更**，`6293b11` 之前生成的对象可被本轮代码正常读取，无需重加密。此项应作为 Phase 0 的交付结论之一记录。

## 3. 新增观察（P7–P10）

### P7　报告版本号四处不一致

- **事实**（`docs/vault-feasibility.md` @ `160ed35`）：
  - 文件头：`文档版本：v1.2`；
  - 「版本与审阅记录」表：最后一行止于 **v1.2**（2026-11-16）；
  - 正文 §7.3：新增块标注「**v1.3 修订**（RV-2026-11-17-02）」；
  - 页脚：仍为「**v1.1** 修订仅限文档内容（按评审 RV-2026-11-16-01）」。
- **影响**：审核基线以版本身份定位；同一文件出现 v1.1 / v1.2 / v1.3 三种自称，后续引用与归档复核会失去锚点。
- **要求**：本次修订统一为 v1.3——头部版本、版本表补 v1.3 行（注明 I1/I3/P6）、页脚改为「v1.3 修订（RV-2026-11-17-02）」，并同步 PROGRESS「当前版本」中的文档版本号。
- **附带**：§7.3 元数据示例 JSON 仍展示 `"h": "sha256..."`，与「h 已废弃」的注记并存；建议示例改为 `"h": ""` 或标注「（废弃，恒空）」，避免读者据示例实现。

### P8　PROGRESS「进行中」与「当前版本」区滞后

- **事实**：
  - 「进行中」仍写「internal/vault 核心完成；**下一步解密读取器 + cmd/mcrypt + local 驱动接入**」——而读取器与 mcrypt 已在 `eacdb07` 落地，`db9da8a` 又完成其修复；
  - 「当前版本」同时存在两条「代码：」，一条为「v0.10.0 已发布（tag v0.10.0）」，另一条仍为「v0.10.0 实现完成（未发版…待闸门⑥）」；
  - 同一区段文档版本写「设计文档 v0.3.1、可行性报告 v1.2」，与设计文档 §3.8 自称 v0.3.2 不一致。
- **影响**：PROGRESS 是外部审核员与 PM 的首读文件，滞后条目会被当作现状引用（本次复核即需交叉验证三处才确认进度）。
- **要求**：清理为单一「代码 / 文档」两行；「进行中」据实改写为「Vault 库层完成；待 local 驱动 OpenRange + Vault 包装层 + webdav 接线，之后方可执行 Phase 0 验收清单」。

### P9　Phase 1 顺序流式契约尚缺实现细节

- **事实**：`design §4.1` 与报告 §7.4 已声明「长连接 + 内部缓冲、顺序播放不按块发请求、随机 Seek 走单块」，但 `RangeSource` 接口仅有 `ReadAt`/`Close`，以下细节未定：
  1. 预读/缓冲大小（建议 4–8 MiB，需与 AX6 内存预算对齐）；
  2. 「连续 / 非连续」的判定规则（相邻 `ReadAt` 偏移差 ≤ 缓冲窗口即视为顺序）；
  3. 缓冲失效时机（反向 Seek、跨块跳跃、403 刷新后重签字）；
  4. 与 `max_streams`（全局信号量）、并发刷新锁的关系。
- **建议**：Phase 1 开工前在 `design §4.1` 补 4–6 行，作为 `upstream.go` 的验收口径；否则实现时仍需二次讨论，易与 Phase 0 的 `DecryptReader` 调用模式（头部 0 / 元数据 64 / 分块 `ChunkCipherOffset`）产生错配。

### P10　`EncryptObject` 对 `meta.S` 失去约束，且失败时残留孤儿对象

- **事实 A**：`EncryptObject` 接收 `size` 与 `meta`，但不再设置 `meta.S`（原末尾回写已删）。若调用方传入与 `size` 不一致的 `meta.S`，密文元数据中的大小与头部 `plain_size` 冲突，直到**读取时**才由 `ValidateMetadata` 拒绝——属 fail-closed，但把可编译期消除的错误推迟到了运行期。
- **事实 B**：明文大小与 `size` 不符时（如文件在 `info.Size()` 与读取之间被改动），函数已写入头与部分分块后才返回错误；`cmdEncrypt` 未删除该半成品，`_mc/o/` 会积累无主对象（因 manifest 最后写，不会破坏一致性，但增加云盘对象数与上传噪音）。
- **建议**：① 在 `SealMeta` 之前 `meta.S = size`（一行，消除不一致来源）；② 加密失败时删除已创建的 `objFull`，或至少在返回错误信息中标注残留路径。
