## 1. 结论摘要

1. **容器方案解决了真问题**：Phase 1 的单根清单是"整棵树全量重加密"，加一个文件要重跑全部。容器方案把加密单元降为"子目录"，新增/删除/更新互不影响，配合懒刷新实现"即传即用"，方向正确。
2. **§5.2 的双通道设计抓住了铁律 7 的坑**：明确"Vault 不得实现 `driver.HealthReporter`，否则 main 对最终 Reader 断言会拿到 Vault 告警而丢失移动驱动的 authorization 过期告警"——这是对既有架构的准确理解，处理得当。
3. **§5.3 对准了真实缺陷**：移动 `Init` 的 `discoverCloudHost` 在过期 token 下可能失败 → 当前 `createAllDrivers` 会把 Init 错误当 fatal（`os.Exit`）。§5.3 的"缓存恢复与校验解耦""空 state + 过期 → 挂载在线 + 过期提示"正是对症，且留有"实现期先核查现状"的余地。
4. **主要缺口在 §5.1 的两个产品决策与两个实现口径**（I1–I4）：若不先定，实现会做错方向或返工。

## 2. 需 PM 拍板的产品决策

### I1　容器方案使"一级目录名"在云盘上明文可见——与 Phase 1 的隐私语义相反

- **事实**：§5.1 约定"容器下只放目录；每个子目录 dir1/dir2 是独立加密单元，各自持有 `_mc`"；且"浏览 `backup/` 走普通目录列表（dir1/dir2 物理可见）"。
- **含义**：dir1/dir2 就是用户上传时的**明文目录名**，直接落在云盘上、也直接展示在 WebDAV 里。而 Phase 1 的单根方案把一切名字（含目录）都藏进加密 manifest。
- **为何是问题**：此前（2026-11-17）PM 明确关心过"子目录名也要加密"。若目录名本身敏感（如"病历""离职证明""xxx"），一级目录名明文泄露仍有实际风险；且 WebDAV 显示的顶层名 = 云盘物理名，二者耦合。
- **需要 PM 拍板**（三选一并写进 §5.1）：
  1. **接受一级目录名明文**（最简单，符合"即传即用"；仅文件与文件内名字受保护）；
  2. **manifest 增加"根显示名"间接层**：云盘物理名可用随机/编号（如 `c01`），manifest 里存"根显示名"（`电影`），WebDAV 展示友好名、云盘只见 `c01`；
  3. **保持单根方案**用于高隐私目录，容器方案仅用于低敏感大目录（两种模式并存）。

### I2　增量粒度 = 子目录，但子目录内仍是全量重加密

- **事实**：容器方案把增量单位从"整棵树"降为"单子目录"，但**一个子目录内部没有文件级增量**——"合并模式 / 内容定址"已记技术债（暂不做）。
- **含义**：一个超大子目录（如 2 TB 的"电影"）加一部新片，仍要**重新加密整个子目录**、重新上传整个 `_mc`（已上传的旧对象可能白传，除非云盘去重）。
- **要求**：① §5.1 明确写"**子目录 = 加密与增量单元，子目录内仍全量重加密**"；② 提示 PM 用**适度粒度**的子目录（按年/按专辑/按类别分），避免单个超大子目录使"即传即用"退化为重传；③ 若 PM 预计会出现超大子目录，则"合并模式"应提前，而非等"上传量成痛点"再启动。

## 3. 需补齐的实现口径

### I3　懒扫描的时长与阻塞边界未定

- **事实**：§5.1 point 2 写"无后台轮询 goroutine"+"TTL 到期后的首次 List 触发扫描，并发 List 串行化"。
- **问题**：扫描在 **List 同步路径**执行；每个子目录的 manifest 读是网络请求（现有 `httpClient` 超时 90 s）。若某个子目录的 `_mc` 读超时，那次 List 会被阻塞到超时；N 个子目录串行最坏 N×90s。PM 场景 ≤10 个虽小，但一个"半死的 CDN 连接"即可让一次目录浏览挂很久。
- **要求**（写进 §5.1）：
  1. manifest 读取使用**独立的短超时**（建议 ≤5s，区别于播放流的 90s）；
  2. 明确"扫描期间，触发的 List 返回旧树还是阻塞"——建议**先返回旧树、扫描异步换树**（去重靠 `refreshMu`，可放一个一次性 goroutine；这与"无后台轮询"不矛盾，只要不是常驻定时器）；
  3. 任一子目录失败不拖累整体（失败子目录记告警、跳过，下周期重试）。

### I4　"与内存摘要（SHA-256）比对"的口径未写明

- **事实**：§5.1 point 2 "读成功 → 与内存摘要（SHA-256）比对：变化 → 原子重建；未变 → 跳过"。
- **问题**：manifest 是 AES-GCM 加密的，**每次 SaveManifest 用随机 nonce → 相同内容密文也不同**。若"摘要"取的是**密文**哈希，则每次都判定"变化"→ 每次都重建（浪费）；若取的是别的不变值，则可能漏判。正确口径必须是**解密后内容**的 SHA-256，或给 manifest 引入**版本/代次字段**（更省：读一个字段即可，不必全文哈希）。
- **要求**：§5.1 明确"摘要 = 解密后清单内容的哈希，或 manifest 增加 generation 字段"，避免实现时对"摘要"的理解分叉。

## 4. 建议（实现/文档细节）

| 编号 | 内容 | 建议 |
|---|---|---|
| P1 | 路径匹配与 `_mc` 层级需重构 | 现在 `findRoot` 只按首段匹配、`isMcPath` 只认 `/_mc`。容器方案变成**两级**（`backup` 容器 → `dirN` 子根 → 虚拟树），`_mc` 出现在第 2 段。§5.1 宜注明"findRoot/roots 结构改为容器→子根两级；isMcPath 按第 2 段判定"，避免实现时另起炉灶或与 Phase 1 代码冲突 |
| P2 | mcrypt 用法变化需写明 | 容器方案下每个子目录**各跑一次 mcrypt**（`-in backup/电影 -out backup/电影`）。§5.1 应写清"即传即用"对应的加密/上传步骤（先传对象后传清单等），否则 PM 不知道新目录怎么产生 |
| P3 | 旧单根迁移方式未说明 | "旧单根结构不再支持，一次性重组织"是 breaking change；需写明迁移方式（mcrypt 逐子目录重跑 / 手工 `mv backup/_mc backup/<名>/_mc` / 提供迁移命令），并同步 README |
| P4 | 容器根出现"文件"的行为未定义 | "容器下只放目录"是约定，但非强制。一个 stray 文件落在 `backup/` 下时（普通 302？告警？）需兜底，与"保留名 `_` 过滤"一起把 `backup/` 列表的完整语义定死 |
| P5 | PROGRESS「进行中」有拼接残留 | 新"Phase 2 已启动"句与旧"Phase 1 验收完成"句串在了一行，内容重复（"真机观察期""55GB 压测（可选）"各出现两次）。PROGRESS 是首读文件，建议清理为两句 |
| P6 | 章节重编号的交叉引用 | 设计文档里程碑由 §5→§6、风险由 §6→§7；请自查 README/CLAUDE/feasibility 是否仍按旧编号引用 design 的 §5/§6（概率低，确认即可） |
