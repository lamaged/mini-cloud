## 2. 内存账复核（报告 §2.2 的两处需修正）

| 每流内存项 | 报告 | 复核结果 | 说明 |
|---|---|---|---|
| 顺序窗口 `u.buf` | 4 MiB | 4 MiB | 持久，`append(u.buf[:0], …)` 复用容量 |
| `doRange` 的 `io.ReadAll` 中转 | ≤ 4 MiB+1 | **峰值约 7 MiB** | `ReadAll` 从 512 B 起倍增；到 4 MiB+1 时按 1.25× 增长，末次 `growslice` 的 **old(≈3.2 MiB) + new(≈4.1 MiB) 同时存在**——崩溃点正是这次 `memmove`，与报告"两块同时存在"方向一致，但量级低估 |
| 密文块 `make([]byte,cLen)` | 1 MiB+16（称"漏算"） | 1 MiB+16（**非漏算**） | design §4.1 的"解密块 2 MiB"本就含 cipher+plain；真实漏账是上一条的 ReadAll 双份 |
| 明文块 `open` 结果 | 1 MiB | 1 MiB | 与 cipher 同时存在，构成 2 MiB |
| **每流峰值** | ~10–11 MiB | **~12–13 MiB** | 4 流 ≈ 48–52 MiB 瞬时，叠加基线后接近路由器可用上限 |

**结论**：根因判断（并发解密流 × 单流峰值超预算 → 堆增长期页故障）成立；**A 的价值比报告估计更大**（消除的是 ~7 MiB 的双份而非 4 MiB）。

## 3. 修复方案评审

### 3.1 A（`doRange` 直接读入复用缓冲）——**采纳**

方向正确且收益最大（每流 −4~7 MiB）。实现需满足以下约束，否则会引入新缺陷：

1. **缓冲所有权与发布时机**：`u.buf` 既是"服务读的窗口"又是"下一次写入的目标"。必须先把 `bufStart/bufEnd` 置为无效（或置 0）再开始填充，**填充完成后持锁一次性发布**两个偏移；否则 `readOnce` 的"完整覆盖"判定可能命中半填充缓冲（当前串行契约下不会并发，但这个是**唯一**由 A 引入的新不变式，须写进注释）。
2. **预扩容一次**：`if cap(u.buf) < length+1 { u.buf = make([]byte, 0, length+1) }`，之后 `u.buf = u.buf[:0]` 直接读入，避免再次 `append` 触发 `growslice`。
3. **截断判定改用实际字节数 `n`**：`n < crEnd-crStart+1` → 截断重试（保持 I1 语义）；`n` 由读循环返回，不得再用 `len(data)`。
4. **读循环语义保持**：读至 `length+1` 或 EOF；`resp.Body` 提前结束（短窗口/截断）必须能与 P9 的续拉区分——**建议保留"读满 length+1 才停止"的循环**，与现有 `LimitReader` 语义等价。

契约④（缓冲计入信号量账）仍成立：每流 4 MiB 窗口 + 2 MiB 解密块 = 6 MiB，A 只是把瞬时峰值压回 6 MiB 量级。

### 3.2 B（密文缓冲复用）——**采纳，并建议扩展到明文缓冲**

- 现状：`loadChunk` 每块 `make([]byte, cLen)` + `gcm.Open(nil,…)` 新分配明文 → 每块 2 MiB 垃圾。
- 建议：`DecryptReader` 持 `cbuf`、`pbuf` 两个 grow-only 字段；`gcm.Open(pbuf[:0], …)` 直接复用（`crypto/cipher` 支持传入 dst）。合计 **每流 −2 MiB**，且大幅降低 GC 压力（当前每 0.4 s 产生一轮 5 MiB 垃圾/流）。
- 注意：`r.chunk` 会与 `pbuf` 别名——`Read` 在下一次 `loadChunk` 前已把数据拷给调用方，串行契约下安全；需注释说明"不得在 `Read` 之外持有 `r.chunk`"。

### 3.3 C（`max_streams` 默认 4 → 3）——**建议暂缓，先实测**

- 算术：A+B 后每流 ≈ 6 MiB + 小量瞬时；4 流 ≈ 24–28 MiB。日志显示空闲可用约 30 MB、另有约 93 MB 可回收 cache——**静态看 4 流可容纳**。
- 压测场景"2 播放器 + 1 下载 = 3 流"只是该次试验的特例，不是产品上限；而"客厅电视 + 卧室电视 + 手机 + 网页下载"是合理用法。默认降到 3 属于**功能缩减**，应先拿 A+B 的实测峰值再决定。
- 若实测仍超，再考虑"降默认 + 允许配置"或"按可用内存动态调整窗口"（后者复杂度高，不建议现在做）。

### 3.4 D（`debug.SetMemoryLimit`）——**有条件采纳，取值建议 64 MiB**

- 它是**软上限**：只让 GC 更早介入，**不阻止**单次大分配的瞬时峰值（A 才是治本）。
- 48 MiB 在"4 流 live ≈ 26 MiB"时只剩 1.8× 余量，弱网/GC 抖动下有**抖动风险**（GC 频繁触发会拉高 CPU，且 A53 上代价可观）。建议 **64 MiB**，并在压测时开 `GODEBUG=gctrace=1` 观察 GC 频率与堆曲线。
- 建议顺序：**A + B 合并提交 → 真机压测实测峰值 → 再决定是否加 D**（避免把"治本"和"保险"混在同一次变更里，出问题时难以归因）。

## 4. 新增发现

### E（重要）　`context canceled` 被当作上游异常，触发无谓的换签名与重试

- **证据**：日志行 102–132（同一对象 `6DYP…4.bin` 连续 10+ 次）与行 123–132：
  `跟随下载重定向失败，使用原始URL err="…: context canceled"` 紧随
  `vault upstream: 上游异常，已换签名重试 … err="…: context canceled"`。
  行 949 亦为 `列出目录失败 … context canceled` 被记为 **ERROR**。
- **机制**：`fetchRange` 对所有 error 统一走"清缓冲 → `refreshURL`（天翼/移动 = 一次云盘 API 调用）→ 重试一次"；而 `context.Canceled` 表示**客户端已断开**（播放器 seek/取消），此时重试与换签名毫无意义。
- **影响**：① 每次 seek/取消都可能多一次云盘 API 调用（天翼还要多一次"跟随重定向"请求，日志里成对出现）；② 日志 WARN 刷屏，掩盖真实上游异常；③ 在压测等高频中断场景下放大 API 调用与 CPU。
- **要求**：`fetchRange` 入口判 `ctx.Err() != nil` 或 `errors.Is(err, context.Canceled)` → 直接返回错误，**不刷新、不重试**；`webdav` 侧对取消类错误降级为 Debug 日志（不记为 ERROR）。建议补一条用例：ctx 取消后 `linkCalls` 不增加。

### F（重要，运维）　崩溃即长期宕机——procd/自启优先级应提升

- 本次为 Go `fatal error`（不可 recover），进程直接消失；日志显示直到 04:21:13 才重启（约 14 分钟空窗）。
- 现有部署脚本以 `setsid … &` 启动，**无进程守护**；TODO 中的"procd 开机自启"仍是技术债。
- **建议**：把 procd init 脚本（`respawn`）从"Phase 2 候选"提升为**本缺陷修复的配套项**——低内存设备上任何 fatal 都应被自动拉起，这是比"避免崩溃"更可靠的兜底。

### G（建议）　补运行时内存可观测性

- 本次诊断完全依赖崩溃转储；建议 `-debug` 模式下每 5 分钟 `slog` 一次 `runtime.ReadMemStats`（HeapInuse / HeapSys / NumGC），压测时配合 `GODEBUG=gctrace=1`，下次同类问题可在数分钟内定位。

## 5. 对报告 §4 四项待审问题的回答

1. **内存账与根因是否认同**：认同方向；两处需修正——`io.ReadAll` 峰值是 old+new ≈ 7 MiB（非 4 MiB）；B 的"1 MiB 漏算"表述不准确（design 的 2 MiB 已含 cipher+plain），真正的漏账是 ReadAll 中转。修完这两处，4 流 × 12 MiB ≈ 48 MiB 与"30 MB 可用 + 93 MB cache"的矛盾关系会更清晰。
2. **A 与契约④、mu 保护域**：仍自洽（每流 6 MiB）；但 A 引入"半填充缓冲不可被读"的新不变式，必须显式置无效再填充、填充完持锁发布（见 §3.1 第 1 条）。网络读取期间**不要持 `mu`**（否则信号量/Close 等路径被长时间阻塞）。
3. **C 默认 3 是否合适**：暂缓（见 §3.3）。先 A+B 实测；若实测峰值仍逼近上限，再讨论默认值，且应保留配置可调。
4. **D 是否采纳、48 MiB 是否合理**：采纳为保险，但**放在 A+B 之后**、取值 **64 MiB**；48 MiB 在 4 流场景余量偏薄，有 GC 抖动风险。
